## 2. 验收口径

每项填写“通过 / 待补证 / 不通过”，不要用空白表示通过。全部满足后才计入合格 target：

1. **固件身份**：包的大小、完整 SHA256 和 LFWC ID 对应；打开包后记录选中镜像相对路径、镜像 SHA256、实际版本、硬件修订和地区。文件名与包内内容冲突时先标记待补证。
2. **CVE 对应**：至少 1 个候选能依据官方记录/厂商公告，确认准确型号、硬件分支及当前版本处在受影响范围；包括/不包括边界、beta/hotfix 和地区后缀均须记录。无法确认的关联保留为待补证或剔除。
3. **较新 CVE 的选择**：在“当前版本有证据适用”的集合内选最新 1–2 个，并记录检索日期。不得把型号相同但仅涉及较新版本的 CVE 加进来；某条被否决时重新检索候选。
4. **Interactive**：与 Greenhouse 原表的 `Web=TRUE` 行对应同一包或同一包内镜像的 SHA256，并保存行记录。仅型号、文件名或相似版本命中不能通过。若采用本地重托管证据替代公开实验表，须另行明确验收口径并保存镜像哈希、环境及正常页面交互记录；两类证据分开记录。
5. **多样性**：排查相近型号及共享平台；以设备类别、硬件平台、SoC/架构等实际证据判断，不能只看编号。未解决的相近型号保留问题或替换；替换后重新执行前四项。

本验收不以执行漏洞利用作为要求。正常 Web 交互验证与 CVE 版本证据核对分别记录；如以后另做漏洞复现，其结果另列。

建议先验收 DIR-825、DIR-600、DCS-5020L 三项，形成填写样例，再逐批处理其余目标。
